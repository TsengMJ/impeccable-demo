# Social Video Production Rules
## AI 開源項目社群短影片製作規範 v1.0

### 0. 核心定位

本規範適用於 Claude 使用 Remotion、HyperFrames、OpenFilm、Higgsfield 等工具，將 AI 開源項目研究資料、實測錄影、圖片及其他素材，製作成適合 X、Reels、Shorts 的短影片。

**最重要的原則：影片的任務是讓觀眾產生興趣、理解價值，而不是完整講解研究報告。**

影片應該像一位懂技術、會說故事的創作者在分享發現，而不是產品簡報、教學課程或 AI 自動生成的 PPT。

評價影片品質的優先順序：

1. 觀眾能不能快速理解。
2. 內容是否有價值、可信。
3. 敘事節奏是否吸引人。
4. 畫面是否精緻且易讀。
5. 動畫及特效是否有助於表達。

動畫數量、影片長度、技術細節數量都不屬於成功指標。

---

# 1. Content Selection — 內容篩選

## 1.1 一支影片只講一件事情

每支影片必須先定義：

- **Core Message**：觀眾看完唯一需要記住的事情。
- **Audience Value**：為什麼觀眾要花時間看？
- **Visual Proof**：用什麼畫面證明或展示？
- **Takeaway**：看完後值得採取什麼行動？

如果無法用一句話說明核心訊息，代表選題太發散。

例如介紹 Impeccable：

不好的核心訊息：

「詳細介紹 Impeccable 的全部功能、設計指令、架構、CLI、Rules、Benchmark 和使用方式。」

好的核心訊息：

「Impeccable 讓 Coding Agent 可以用更具體的方式改善 AI 生成的 UI。」

整支影片應該圍繞這個訊息展開。

## 1.2 資訊優先級

將研究資料分成三層。

**P0：必須保留**

- 產品是什麼、解決什麼問題。
- 最有意思的 1–2 個能力。
- 最直觀的展示或實測結果。
- 會影響觀眾判斷的重要限制。

**P1：有空間才保留**

- 簡單的工作原理。
- 與其他工具的關鍵差異。
- 一個值得注意的技術設計。
- 有意義的數據。

**P2：預設刪除**

- 詳細安裝流程。
- 完整技術架構。
- 所有功能列表。
- 程式碼內部實作。
- 不影響結論的實驗設定。
- 大量 Benchmark 數字。
- GitHub Stars、Forks、Commit 等無助於本次敘事的資料。
- 作者背景和冗長的產品歷史。

P2 不代表沒有價值，而是不適合放進這支短影片。

這些內容可以移到貼文正文、技術文章或下一支影片。

## 1.3 技術細節保留條件

每個技術細節都需要回答：

**「觀眾知道這個細節之後，會不會更理解產品的價值、差異或限制？」**

如果不會，直接刪除。

例如：

不建議：

「Firecrawl 使用 Playwright、Redis、RabbitMQ 和 Worker Queue。」

建議：

「它能把需要 JavaScript 渲染的網頁，整理成 Agent 可以直接閱讀的 Markdown。」

第一句偏向內部實作。

第二句直接讓觀眾理解能力和使用價值。

若技術本身就是影片主題，可以保留並解釋，但不得預設所有觀眾都需要了解。

# 2. Duration & Script — 時長與腳本

## 2.1 影片長度

預設規格：

| 類型 | 建議長度 |
|---|---|
| 快速發現 / 工具推薦 | 20–35 秒 |
| 單一功能展示 | 30–45 秒 |
| 項目介紹 + 實測 | 45–60 秒 |
| 深入比較或複雜實驗 | 60–90 秒，需明確理由 |

**一般項目分享預設 45–60 秒。**

超過 75 秒時，必須優先檢查能否刪減、拆成兩支影片，或把內容移至長文。

不得因為研究資料很多，就自動延長影片。

## 2.2 標準敘事結構

以 60 秒影片為例：

| 時間 | 階段 | 任務 |
|---|---|---|
| 0–3s | Hook | 讓觀眾產生好奇 |
| 3–10s | Problem | 讓觀眾理解痛點 |
| 10–22s | Solution | 說明項目如何解決問題 |
| 22–45s | Demo / Proof | 展示最值得看的功能或結果 |
| 45–55s | Takeaway | 真實發現、價值與限制 |
| 55–60s | CTA | 引導收藏、研究或查看完整內容 |

這是預設節奏，可以依素材調整，不是每支影片都要機械地切成六段。

**禁止開場先花 5–10 秒介紹專案名稱、作者、GitHub 星數、Logo。**

優先從問題、實際效果、意外發現或強烈的視覺對比開始。

## 2.3 Voiceover Rules

- 60 秒影片建議先以約 140–190 個中文字作為初稿預算，實際長度以自然朗讀及停頓測試為準。
- 使用自然口語，不用 README 或研究報告的書面語。
- 一句話只表達一個重點。
- 避免連續堆疊三個以上專業名詞。
- 能用具體例子解釋，就不要先用抽象定義。
- 刪除無資訊價值的過場句，例如「首先讓我們來了解一下」。
- 不要為了壓進時長而把語速加快到不自然。

**優先刪內容，而不是加快旁白。**

## 2.4 Script Compression Gate

腳本完成後，必須執行三輪精簡：

1. 移除不影響核心結論的內容。
2. 移除能直接靠畫面理解、無須旁白重複解說的內容。
3. 移除沒有明確作用的轉場句。

若刪除某一句後，觀眾仍能理解完整故事，就優先刪掉。

在腳本沒有通過精簡前，不應開始製作正式動畫。

# 3. Visual Storytelling — 視覺敘事

## 3.1 一個畫面只有一個焦點

每個 Scene 都必須回答：

**「觀眾第一眼應該看哪裡？」**

禁止：

- 同時展示多張資訊卡和大量文字。
- 一個畫面塞入完整技術架構與解說。
- 把 README 或 Markdown 直接變成 PPT。
- 同時播放多個互相競爭的動畫。
- 使用太多沒有層級的標籤。

優先使用：

- 單一大標題。
- 局部放大的產品畫面。
- 一個主要數據。
- 一個清楚的前後比較。
- 一條簡單的動畫流程。

有多個重點時，應該依序出現，不要全部同時展示。

## 3.2 文字層級

每個畫面最多三層資訊：

1. **Headline**：主要訊息。
2. **Supporting Text**：補充說明。
3. **Caption / Label**：必要的註解。

建議：

- Headline 盡量控制在 14 個中文字以內。
- Supporting Text 最多兩行。
- 一般內容文字不超過 24 個中文字。
- 避免同一畫面同時出現超過三個需要閱讀的文字區塊。
- 超過限制時，優先拆 Scene，不要縮小字體。

以上是內部製作目標，不是平台硬性限制。

## 3.3 Typography

針對 1080 × 1920 直式影片的設計起點：

| 類型 | 建議字級 |
|---|---|
| 主要標題 | 84–110px |
| 重點說明 | 44–64px |
| 字幕 | 約 44–58px |
| 小型標籤 | 約 32–40px |

要求：

- 必須在手機正常觀看尺寸下可讀。
- 中文字體筆畫清楚。
- 不要使用過細字重。
- 避免背景和文字對比不足。
- 不要靠縮小文字解決排版問題。

## 3.4 Layout & Safe Area

- 預設採用 9:16、1080 × 1920。
- 重要內容距離左右邊緣至少約 100–120px。
- 預留頂部約 250px、底部約 300px 的保守 UI 避讓區，並依實際平台預覽調整。
- 不將關鍵字幕放在平台按鈕或貼文資訊覆蓋區域。
- 需要完整呈現橫向螢幕錄影時，使用裁切放大、重新構圖或分段展示。
- 不要直接把整張 16:9 桌面截圖縮小塞進直式影片。

## 3.5 Visual Language

預設視覺風格：

**Modern Tech Editorial / Premium Product Demo**

特徵：

- 清楚、有層次的排版。
- 大字標題。
- 足夠留白。
- 有質感的背景。
- 適度使用空間透視和鏡頭運動。
- 將真實產品素材作為視覺主角。
- 以少量重點色建立視覺辨識度。

避免：

- 每個畫面都是發光玻璃卡片。
- 無意義的粒子和光線。
- 過度複雜的科技背景。
- 所有元件一直漂浮、旋轉。
- 過度使用相同的卡片進場動畫。

**科技感不等於滿畫面特效。**

# 4. Motion Design — 動畫規範

## 4.1 動畫必須有目的

每段動畫至少達成一項目的：

- **Direct Attention**：引導觀眾注意重點。
- **Explain**：解釋功能或資料流程。
- **Compare**：展示前後差異。
- **Emphasize**：強調重要結果。
- **Transition**：讓不同段落自然銜接。

如果動畫沒有幫助以上任何一項，就考慮移除。

## 4.2 常用動畫形式

| 內容 | 優先動畫 |
|---|---|
| 新工具介紹 | Logo + Product Hero |
| UI 畫面 | Zoom / Pan / Focus Highlight |
| Before / After | Split Reveal / Slider |
| 工作流程 | Progressive Flow |
| 核心數字 | Number Reveal |
| 功能介紹 | Product Demo + Annotation |
| 技術比較 | Side-by-Side / Sequential Comparison |
| 核心結論 | Large Typography + Minimal Motion |

優先選擇符合內容的動畫，而不是反過來為了使用特效硬找素材。

## 4.3 Visual Rhythm

- 前 3 秒內應有明確的視覺或資訊變化。
- 一般敘事段落可每 3–6 秒安排一次有意義的視覺變化。
- 重要的 Before / After 或實測結果應保留足夠閱讀時間。
- 有價值的操作畫面不應為了節奏而過度加速。
- 同一套動畫不要每個 Scene 都重複使用。
- 允許短暫停頓，讓重要結果更有力量。

節奏不是一直切鏡頭，而是持續提供新的資訊與視覺重點。

## 4.4 Animation Quality

- 使用自然的 Easing。
- 避免元素突然開始或停止運動。
- 大部分裝飾動畫應短而清晰。
- 文字進場後要保留閱讀時間。
- 進場、停留、離場都需要合理時間。
- 避免過度閃爍、畫面震動或造成不適的效果。

# 5. Asset Usage — 素材使用

## 5.1 優先使用真實素材

優先級：

1. 真實產品錄影。
2. 真實實測結果。
3. 真實 Before / After。
4. 官方產品素材。
5. 程式化圖解與動畫。
6. 生成式 AI 視覺素材。

不需要把每個畫面都交給影片生成模型。

## 5.2 Screenshot / Screen Recording

- 截圖必須裁切到實際重點。
- 可以用 Zoom、Pan、Highlight 引導注意。
- 長時間操作流程應剪掉等待和無意義步驟。
- Command Line 只保留必要指令和結果。
- 程式碼只展示真正影響理解的部分。
- Before / After 必須使用相同或可比較的畫面條件。

## 5.3 Generative AI Usage

Remotion / HyperFrames 優先負責：

- UI 展示。
- 動畫標題。
- 字幕。
- 數據視覺化。
- 流程圖。
- 分割比較。
- 素材合成。

Higgsfield 等生成式模型主要用於：

- 特殊背景。
- 氛圍鏡頭。
- 風格化 B-roll。
- 需要生成不存在畫面的片段。

不得使用 AI 生成內容冒充真實實測結果。

# 6. Audio & Captions

## 6.1 旁白

- 自然、清楚、可信。
- 不要像朗讀技術文件。
- 適當強調核心發現。
- 重要畫面出現時，可以短暫減少旁白。
- 背景音樂不得干擾人聲。

## 6.2 字幕

- 全片語音必須有準確字幕。
- 字幕與人聲同步。
- 優先採用短句或分段字幕。
- 重要關鍵字可以有不同顏色或字重。
- 不要每個字都加彈跳特效。
- 字幕不得和重點圖卡重疊。

## 6.3 文字不應重複堆疊

Voiceover、字幕、Headline 不應全部重複相同內容。

例如：

旁白：「這個工具可以幫 Coding Agent 改善 UI。」

Headline：「讓 AI 做的 UI 更有設計感」

畫面：實際 Before / After。

這比同時用三種文字重複同一句話更有效。

# 7. Production Workflow

必須依照以下順序製作。

### Stage 1：Content Distillation

從研究報告提取：

- 一個核心訊息。
- 觀眾痛點。
- 1–2 個重要功能。
- 一個最有力的證據。
- 重要限制。

將其他資料移出影片腳本。

### Stage 2：Script

產出精簡的旁白稿。

檢查：

- 是否符合時長？
- 前 3 秒是否有吸引力？
- 是否只圍繞一個核心觀點？
- 有沒有不必要的技術細節？

不符合則重寫。

### Stage 3：Storyboard

每個 Scene 必須包含：

| 欄位 | 內容 |
|---|---|
| Time | 開始與結束時間 |
| Voiceover | 旁白 |
| Key Message | 觀眾需要理解什麼 |
| Visual | 使用的圖片、影片、文字 |
| Animation | 動畫方式 |
| Asset Source | 對應的真實素材 |
| Purpose | 為什麼需要這個 Scene |

每個 Scene 必須具備清楚的資訊或敘事功能。

### Stage 4：Visual Design

先確定：

- 全片設計風格。
- 字體系統。
- 配色。
- 資訊層級。
- 主要 Scene Layout。
- 動畫語言。

優先製作 Hook、Demo、Result 三個代表性畫面，確認視覺品質後，再延伸到其他 Scene。

### Stage 5：Animation & Assembly

依照 Storyboard 製作動畫。

不得因為可以製作某種特效，就自行擴充腳本內容或延長影片。

### Stage 6：QA & Revision

完成後必須實際檢查影片，而不是只確認渲染成功。

至少檢查：

- 開頭是否足夠清楚。
- 是否有無價值的 Scene。
- 文字是否清晰。
- 動畫是否干擾閱讀。
- 字幕是否準確。
- 畫面是否與旁白同步。
- 截圖及實測數據是否真實。
- 是否有文字溢出、畫面遮擋、空白影格。
- 背景音樂是否干擾人聲。
- 影片是否可以再縮短。

需要時重新製作，不要只依賴第一次生成的結果。

# 8. Quality Gate — 驗收標準

影片交付前必須通過以下檢查。

| 指標 | 通過條件 |
|---|---|
| 核心訊息 | 能用一句話說明 |
| 影片長度 | 符合事先設定的時間預算 |
| Hook | 前 3 秒直接提供興趣點 |
| 資訊密度 | 沒有冗長背景或不必要的實作細節 |
| 視覺層級 | 每個 Scene 有一個明確焦點 |
| 字幕 | 可讀、正確、同步 |
| 動畫 | 具有敘事目的 |
| 真實性 | 不捏造產品能力或實測結果 |
| 節奏 | 不拖沓，也不過度快速 |
| 行動引導 | 觀眾知道是否值得進一步了解 |

**以下情況必須退回修改：**

- 影片超時卻沒有新增觀眾價值。
- 連續多個 Scene 只有文字卡片。
- 直接把研究報告內容依序朗讀。
- 手機觀看時無法閱讀文字。
- 沒有明確示範，卻花很多時間描述功能。
- 加入大量動畫，但看完仍不知道產品有什麼用。
- 把官方聲明或模擬畫面描述成實際驗證成果。

# 9. 成效回饋與持續改善

影片發布後，有數據時追蹤：

- 前幾秒留存。
- 平均觀看時間。
- 完播率。
- 重播率。
- 收藏與分享。
- 導向 Repository 或文章的點擊。

根據問題調整：

- 開頭流失高：檢查 Hook 是否太慢。
- 中段流失高：檢查內容過密或 Demo 太長。
- 看完但互動低：檢查觀眾是否得到值得收藏或分享的發現。
- 有觀看但不理解產品：檢查訊息層級和具體展示。

不要只追求觀看數，還要觀察是否吸引到真正對項目有興趣的受眾。

---

# 10. Final Principle

**Social Video ≠ Research Report ≠ Tutorial**

- Research Report：追求完整、證據與深度。
- Tutorial：追求操作步驟與可重現性。
- Social Video：追求快速理解、興趣、可信的視覺證據。

如果觀眾只看完 30 秒，就能知道這個項目做什麼、為什麼有意思、值不值得繼續研究，這支影片已經完成了重要任務。

**寧可把一個亮點講清楚，也不要把十個功能講得沒人想聽。**
